# 도메인 문서

엔지니어링 스킬들이 코드베이스를 탐색할 때 이 저장소의 도메인 문서를 어떻게 참고해야 하는지 정리한다.

## 탐색 전에 읽을 것

- 저장소 루트의 **`CONTEXT.md`**, 또는
- 루트에 **`CONTEXT-MAP.md`** 가 있다면 그것 — 컨텍스트별 `CONTEXT.md`를 가리킨다. 주제와 관련된 것들을 각각 읽는다.
- **`docs/adr/`** — 작업하려는 영역과 관련된 ADR을 읽는다. 멀티 컨텍스트 저장소라면 `lib/<context>/docs/adr/`의 컨텍스트별 결정도 확인한다.

이 파일들이 없으면 **조용히 진행한다.** 부재를 지적하지 말고, 먼저 만들라고 제안하지도 않는다. `/domain-modeling` 스킬(`/grill-with-docs`, `/improve-codebase-architecture`를 통해 도달)이 실제로 용어나 결정이 정리될 때 lazy하게 생성한다.

## 파일 구조

싱글 컨텍스트 저장소 (이 저장소가 여기 해당):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-theme-persistence.md
│   └── 0002-riverpod-codegen.md
└── lib/
```

멀티 컨텍스트 저장소 (루트에 `CONTEXT-MAP.md` 가 존재):

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← 시스템 전역 결정
└── lib/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← 컨텍스트 한정 결정
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 용어집의 어휘를 사용할 것

출력물이 도메인 개념을 지칭할 때(이슈 제목, 리팩토링 제안, 가설, 테스트 이름 등) `CONTEXT.md`에 정의된 용어를 그대로 쓴다. 용어집이 명시적으로 피하는 동의어로 표류하지 않는다.

필요한 개념이 아직 용어집에 없다면 그건 신호다 — 프로젝트가 쓰지 않는 언어를 만들어내고 있거나(재고할 것), 실제로 빠진 개념이 있는 것이다(`/domain-modeling`을 위해 기록해 둘 것).

## ADR 충돌은 드러낼 것

출력물이 기존 ADR과 모순된다면 조용히 덮어쓰지 말고 명시적으로 언급한다:
